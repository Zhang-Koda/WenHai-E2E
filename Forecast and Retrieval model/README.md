# WenHai-E2E

WenHai-E2E is an end-to-end machine learning global ocean forecast system (GOFS)
at 1/12 degree resolution. Machine learning models have reached competitive
forecast accuracy at a fraction of the computational cost of numerical GOFSs,
but they cannot operate on their own: they still depend on initial conditions
generated by a numerical GOFS. WenHai-E2E replaces that entire pipeline at
deployment time, making eddy-resolving global ocean forecasts directly from
multi-source heterogeneous ocean observations, and outperforms a
state-of-the-art numerical GOFS in forecast accuracy.

The system runs in two stages. A fusion stage turns multi-source heterogeneous
observations - in situ temperature and salinity profiles, along-track and
gridded sea level anomaly, and L4 sea surface temperature - into a global ocean
state, without any operational initial condition from a numerical GOFS. A
forecast stage then advances that state, and, like
[WenHai](https://github.com/Cuiyingzhe/WenHai), utilizes both physical formulae
and a deep learning model: air-sea fluxes are computed with bulk formulae, and
a Swin-Transformer predicts the daily increment.

This repository releases the forecast stage. Two ONNX models are used at each
step. `WenHai_tsssh.onnx` predicts the daily increment of temperature, salinity
and sea surface height over 40 levels; `WenHai_uv.onnx` then diagnoses the zonal
and meridional velocities from the updated state. Both run on the native
2041 x 4320 grid - the polar and circular paddings are part of the exported
graph. The sample initial condition provided here is the output of the fusion
stage, so the forecast reproduces a deployment-time cycle from that point on -
no numerical GOFS is involved anywhere in the chain.

## Files

| file | description |
| --- | --- |
| `inference.py` | forecast script |
| `environment.yml` | conda environment |
| `WenHai_tsssh.onnx` | temperature / salinity / sea surface height model |
| `WenHai_uv.onnx` | velocity diagnosis model |
| `sample_fusion_zos.nc` | sample initial ocean state |
| `sample_IFS_d0083.nc` | sample atmospheric forcing |
| `mask.nc` | land-sea mask, 40 levels |
| `max_GLORYS.npy`, `min_GLORYS.npy` | ocean normalization bounds, `[U*40, V*40, T*40, S*40, SSH]` |
| `max_flux.npy`, `min_flux.npy` | air-sea flux normalization bounds |

## Usage

```bash
python inference.py \
    --init_path    sample_fusion_zos.nc \
    --forcing_path sample_IFS_d0083.nc \
    --output_path  ./output
```

Forecasts are written to
`{output_path}/fcst{date}/fcst{date}_lead{n}_byWenHai-E2E.nc`, one file per
lead, each holding `thetao`, `so`, `uo`, `vo` and `zos` on a `time`, `depth`,
`latitude`, `longitude` grid.

The forecast length is `len(forcing.time) - 1`; the last forcing step only
drives the fluxes of the final velocity diagnosis. The sample forcing has 11
steps and therefore produces leads 0 to 10. Lead 0 is the initial state itself:
no prognostic step is taken, but the model still diagnoses `uo` and `vo` from
it, so the initial velocities are available on the same grid as the forecasts.

`onnxruntime-gpu` is used when a CUDA device is visible (about 3 s per model
call) and `onnxruntime` on CPU otherwise (about 2.5 min).

## Variables

The ocean state uses GLORYS names, in physical units, with land set to NaN.

| name | meaning | units |
| --- | --- | --- |
| `thetao` | sea water potential temperature | degrees_C |
| `so` | sea water salinity | 1e-3 (practical salinity unit) |
| `uo` | eastward sea water velocity | m s-1 |
| `vo` | northward sea water velocity | m s-1 |
| `zos` | sea surface height above geoid | m |

`thetao`, `so`, `uo` and `vo` are given on 40 depth levels; `zos` is a surface
field. The horizontal grid is 2041 x 4320 at 1/12 degree, spanning 80S to 90N
and 180W to 180E.

The 40 levels, in metres:

```

 11.405   13.467   15.810   18.496   21.599   25.211   29.445   34.434
 40.344   47.374   55.764   65.807   77.854   92.326  109.729  130.666
155.851  186.126  222.475  266.040  318.127  380.213  453.938  541.089
643.567  763.333  902.339 1062.440 1245.291 1452.251 1684.284 1941.893
```

The atmospheric forcing uses the ECMWF short names.

| name | meaning | units |
| --- | --- | --- |
| `t2m` | 2 metre temperature | K |
| `d2m` | 2 metre dewpoint temperature | K |
| `u10` | 10 metre U wind component | m s-1 |
| `v10` | 10 metre V wind component | m s-1 |
| `msl` | mean sea level pressure | Pa |
| `mtpr` | mean total precipitation rate | kg m-2 s-1 |
| `ssr` | surface net short-wave (solar) radiation | J m-2 |
| `strd` | surface long-wave (thermal) radiation downwards | J m-2 |

## Input data

`sample_fusion_zos.nc` holds `thetao`, `so` and `zos` for 2025-01-01 in physical
units, with land set to NaN, on the GLORYS12V1 1/12 degree grid. None of it is a
numerical reanalysis: `thetao` and `so` are the fusion stage's analysis of the
observations available on that date, and `zos` is the DUACS L4 sea level anomaly
of that date added to a mean dynamic topography.

`sample_IFS_d0083.nc` holds `t2m`, `d2m`, `u10`, `v10`, `msl`, `mtpr`, `ssr`
and `strd`. The eight fields cover successive 24 h windows of a single ECMWF
IFS HRES 00z forecast - 0-24h through 240-264h - remapped from 0.25 degree to
the GLORYS grid, with the longitude boundary treated as circular.

The two kinds of field are reduced differently. `t2m`, `d2m`, `u10`, `v10` and
`msl` are instantaneous, and are averaged over the samples in the window.
`ssr`, `strd` and `mtpr` are accumulated since the start of the forecast, and
are differenced across the window: `ssr` and `strd` are divided by 24 to give
the mean hourly accumulation in J m-2, which `inference.py` divides by 3600 to
reach W m-2; `mtpr` is the precipitation accumulated over the window expressed
as a mean rate in kg m-2 s-1.

The forcing is a forecast, not a reanalysis, so the model runs in the same
configuration it would use operationally. Any file with these eight variables
on this grid and a `time` dimension can be passed instead.
